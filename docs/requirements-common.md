# 런치캐치 — 공통/시스템 요구사항 명세서

> 전체 시스템 공통 기능

## 인증/인가

### 토큰 인증 및 역할 기반 접근 제어
- **우선순위:** 필수
- **설명:** 시스템이 접근 자격과 갱신 자격으로 요청자를 인증하고 역할별 기능 접근을 제어한다
- **입력:** Access Token, Refresh Token, 역할(SUPER_ADMIN/ADMIN/OWNER/USER)
- **선택:** 없음
- **상세:**
  - 단일 기준: Access Token은 JWT 30분
  - Refresh Token은 Opaque Token으로 인메모리 캐시에 저장하고 SHA-256 해시를 관계형 DB에 백업하며, 관리자 1일, 점주 14일, 사용자 14일(자동 로그인 미체크 시 세션 쿠키)
  - 두 토큰은 HttpOnly, SameSite=Strict 쿠키로 전달하고 Rotation을 적용한다
  - 로그아웃 시 Refresh Token을 폐기하고 Access Token valid-after cutoff를 저장한다
  - 프레임워크의 메서드 단위 인가로 API별 접근을 제어한다
  - 역할별 로그인 행은 이 정책을 참조한다
- **예외:** 폐기된 Refresh Token을 사용하면 해당 계정의 전체 세션 로그아웃. 역할이 맞지 않으면 접근 거부(403)

## 캠페인 상태

### 캠페인 상태 전이
- **우선순위:** 필수
- **설명:** 시스템이 캠페인 상태(DRAFT/SCHEDULED/ACTIVE/PAUSED/ENDED)를 서버에서만 전이한다
- **입력:** 캠페인 ID, 현재 상태, 전이 상태, 전이 주체, PAUSED 사유(ADMIN/OWNER/NO_POINTS)
- **선택:** 사유
- **상세:**
  - 상태: DRAFT, SCHEDULED(자동 검수 통과, 시작 대기), ACTIVE, PAUSED, ENDED
  - 허용 전이: DRAFT -> SCHEDULED(자동 검수 통과), SCHEDULED -> ACTIVE(집행 시작일 00:00 스케줄러, D-1 23:59까지 SCHEDULED인 건만), ACTIVE -> PAUSED(관리자/점주/포인트 부족), PAUSED -> ACTIVE, ACTIVE/PAUSED -> ENDED(집행 기간 종료, 새 캠페인 ACTIVE)
  - 당일 예산 소진과 수량 소진은 상태 전이 없이 당일 노출만 중단한다
  - 모든 전이는 감사 로그로 기록한다
- **예외:** 허용되지 않은 캠페인 상태 전이 요청은 409 반환

## 피드 엔진

### 피드 구성 (배분 슬롯 배정)
- **우선순위:** 필수
- **설명:** 시스템이 공정성에 따라 배분 슬롯을 배정한다
- **입력:** 사용자 위치, 반경, 활성 캠페인 목록, 캠페인별 예산 소진 진행률, 사용자별 당일 노출/패스 이력, 차단 가게
- **선택:** 카테고리 필터
- **상세:**
  - 후보는 00:00 배치가 만든 그날의 피드 후보 스냅샷에서 찾는다. 스냅샷에는 그날 ACTIVE인 캠페인과 그 가게의 위치, 카테고리, 노출 대상 조건이 들어 있다. 서빙 중에는 다른 도메인의 테이블을 읽지 않는다
  - 후보 조건: 현재 시각이 서빙 시간대(10:00~12:59) 안, 선착순 쿠폰 발급 잔여 수량 > 0, 사용자가 캠페인 노출 대상(점주 반경, 성별, 연령대 일치)에 해당하고 사용자 반경 내, 차단 가게 아님, 예산 소진 진행률 1.2 이하, 오늘 노출 횟수를 다 채우지 않음, 그날 이미 패스하지 않음
  - 우선순위: 예산 소진 진행률 오름차순, 동률 시 등록 시각 오름차순. 신규 우선 노출(첫 3일) 캠페인은 진행률에 0.8을 곱해 앞순위로 당긴다
  - 사용자 반경 내 후보 10개 미만이면 1->2->3->5km 확장(점주 반경 밖 사용자에게는 미노출)
  - 노출 대상을 좁게 정한 캠페인은 후보에 드는 횟수가 적어 진행률이 낮게 유지되므로 후보에 들 때는 자연히 앞순위가 된다(별도 보정 없음)
  - 예산 크기는 하루 노출 총량을 정하고 진행률은 노출 순서를 정한다. 예산이 큰 캠페인은 당일 예산을 늦게 소진해 후보에 더 오래 남으므로 결과적으로 더 많이 노출되지만, 같은 시점의 배정 순서를 앞당기지는 못한다
  - 하루가 시작되는 시점에는 모든 캠페인의 진행률이 0으로 같아 등록이 빠른 캠페인이 먼저 배정되지만, 노출이 시작되면 진행률이 갈라지므로 이 영향은 하루 첫 회차에 한정된다
- **예외:** 배분 슬롯 후보 캠페인이 3개 미만이면 남는 슬롯을 관련성 슬롯으로 전환. 후보가 0개이면 피드 전체를 관련성 슬롯으로 구성

### 피드 구성 (관련성 정렬)
- **우선순위:** 필수
- **설명:** 시스템이 관련성 점수로 관련성 슬롯을 정렬한다
- **입력:** 거리, 카테고리, 할인 유형/값, 사용자 찜/패스 이력(30일), 필터
- **선택:** 없음
- **상세:**
  - 점수 = 거리 45% + 카테고리 선호도 35% + 할인 매력도 20% (시간 적합도는 오픈 시각 고정으로 삭제)
  - 거리 점수는 사용자와 가게가 가까울수록 1에 가깝고 사용자 반경 끝이면 0이다
  - 카테고리 선호도는 최근 30일 동안 그 카테고리 카드를 찜한 비율(찜 수 / (찜 수 + 패스 수))이며 기록이 5건 미만이면 중립값 0.5로 본다
  - 할인 매력도는 할인율을 0~1로 환산한 값이다
  - 배분 슬롯에 이미 배정된 캠페인은 관련성 슬롯에 중복 배정하지 않고, 노출 횟수 상한도 동일하게 적용한다
  - 관심 가게 등록은 관련성 점수에 반영하지 않는다. 카테고리 선호도와 신호가 중복되고, 관심 등록이 없는 신규 가게가 구조적으로 불리해지기 때문이다. 관심 가게에는 알림과 전용 목록으로 접근 경로를 제공한다
- **예외:** 관련성 계산에 사용자 위치 이력은 사용하지 않고 현재 세션 위치만 사용. 점주 비용에 의한 순위 상승은 범위 밖

## 예산 소진 속도 조절

### 하루 예산 배분 및 예산 소진 진행률 계산
- **우선순위:** 필수
- **설명:** 시스템이 캠페인별 하루 예산을 시간대별로 나누고, 계획 대비 얼마나 썼는지를 나타내는 예산 소진 진행률을 계산한다
- **입력:** 캠페인 ID, 하루 예산, 당일 적용 단가, 집행 기간, 당일 누적 소진 포인트
- **선택:** 시간대 가중치 설정값
- **상세:**
  - 매일 00:00 하루 예산 초기화(미소진분 이월 없음. 점주가 바꾼 값이 예약돼 있으면 이때 적용한다), 일별 노출 목표 = 하루 예산 / 단가
  - 예산 소진 진행률 = 지금까지 실제로 쓴 포인트 / 지금까지 썼어야 할 포인트(하루 예산을 시간대 가중치로 나눈 계획값을 현재 시각까지 더한 값)
  - 예: 하루 예산 30,000포인트를 10시, 11시, 12시에 균등 배분하면 11시 30분까지 썼어야 할 포인트는 15,000이고, 실제 6,000을 썼으면 진행률은 0.4다. 값이 낮을수록 계획 대비 덜 쓴 것이라 배분 슬롯을 먼저 받는다. 금액이 아니라 비율이므로 예산이 큰 캠페인이 순서를 앞당기지 못한다
  - 서빙 시간대 10:00~12:59, 시간대 가중치(하루 예산을 서빙 시간대별로 나누는 비율) 기본값 균등(10시 34%, 11시 33%, 12시 33%), 운영 데이터로 조정
  - 당일 소진과 점주 잔액의 실시간 카운터는 예산이 단독으로 소유한다. 다른 도메인은 자기 카운터를 만들지 않고 예산이 제공하는 조회 기능으로 읽는다. 실시간 카운터는 인메모리 캐시에 두고 원본은 정산의 포인트 원장이다
- **예외:** 인메모리 캐시 장애 시 관계형 DB의 원장과 노출 로그로 카운터를 재구성한다. 재구성 값은 정산의 대조 작업이 계산해 예산에 통보하고 예산이 자기 카운터에 반영한다. 장애 직후에는 그 작업을 수동으로 실행한다. 서빙 시간대 밖에는 피드 자체를 제공하지 않음. 캠페인의 당일 소진이 하루 예산에 도달하면 해당 캠페인의 당일 노출 중단

## 노출 수집

### 노출 이벤트 수집 및 검증
- **우선순위:** 필수
- **설명:** 시스템이 카드 표시 이벤트를 수신하여 유효/무효를 판정하고 저장한다
- **입력:** serve_id, campaign_id, user_id, displayed_at, 반올림 좌표
- **선택:** viewed_ms(참고 지표)
- **상세:**
  - 노출 이벤트를 1건씩 받아 검증한다
  - 검증은 두 가지뿐이다. (a) 인메모리 캐시의 serve 기록(키: serve_id, 유효 기간 = 노출 인정 시간 30분)이 존재하는지, 없으면 EXPIRED_OR_UNKNOWN. (b) serve 기록의 사용자와 요청 사용자가 같은지, 다르면 NOT_OWNER
  - serve 기록은 광고 서빙이 피드를 내려줄 때 만든 자기 데이터이므로 다른 도메인을 조회하지 않는다
  - serve_id UNIQUE 제약으로 중복은 저장 거부
  - 유효 판정 시 예산의 과금 가능 판정을 호출하고, 돌려받은 과금 상태를 노출 로그에 함께 기록한다
  - 초당 10,000건, p95 100ms
  - 좌표는 소수점 3자리로 반올림해 저장
  - 유효/무효 결과를 202로 반환하되, 화면을 벗어나면서 보낸 요청은 클라이언트가 응답을 받지 못할 수 있으므로 응답에 의존하지 않는다
  - 향후 요청 수가 문제가 되면 여러 건을 묶어 받는 방식으로 전환할 수 있으며, 검증과 멱등 처리는 동일하다
- **예외:** 무효 노출도 사유와 함께 저장(삭제 없음)하되 포인트는 차감하지 않음. 유효 노출 중 하루 예산에 도달했거나 잔액이 부족한 건은 미과금으로 저장하며, 리포트에는 노출 수로 집계하되 과금액에는 반영하지 않는다

## 이벤트 로그

### 전환 퍼널 이벤트 로깅
- **우선순위:** 필수
- **설명:** 시스템이 노출부터 사용까지 퍼널 이벤트를 추적 가능하게 저장한다
- **입력:** event_id, event_type, occurred_at, received_at, user_id, campaign_id, store_id
- **선택:** 상위 단계 식별자(serve_id, wish_id, issue_id)
- **상세:**
  - 이벤트 유형: impression, wish, pass, issue_open, issue, redeem, expire, map_view, wishlist_view, notification_sent, poster_open
  - 추가 전용(append-only)이며 정정은 정정 이벤트를 추가한다
  - 관계형 DB에 월 단위 RANGE 파티셔닝으로 저장하고 13개월 보존
- **예외:** 동일 event_id의 이벤트 중복 수신은 1건만 처리. 이벤트 로그의 수정/삭제 기능은 제공하지 않음

## 스케줄러

### 하루 시간표 스케줄러
- **우선순위:** 필수
- **설명:** 시스템이 00:00 활성화와 예산 초기화, 10:50 오픈 알림, 11:00 선착순 오픈, 캠페인별 사용 종료 시각 쿠폰 만료를 집행한다
- **입력:** 캠페인 ID, issue_id, 설정값(서빙 시간대, 오픈 시각, 사용 가능 시간, 알림 선행 시간)
- **선택:** 없음
- **상세:**
  - 00:00 작업은 다음 순서로 실행하며, 이 순서는 의존 관계이므로 임의로 바꿀 수 없다
  - (1) 집행 기간이 끝난 캠페인 ENDED (잔여 포인트는 점주 잔액으로 유지)
  - (2) D-1 23:59까지 SCHEDULED인 캠페인 ACTIVE 전환 (기존 ACTIVE는 ENDED)
  - (3) 하루 예산 초기화 (전일 미소진분 이월 없음. 점주가 바꾼 값이 예약돼 있으면 이때 적용한다)
  - (4) 시간대별 목표 소진 포인트 계산 -> (2)에서 확정된 ACTIVE 캠페인만 대상
  - (5) 포인트 부족으로 중단된 캠페인 재개 검사
  - (6) 그날의 피드 후보 스냅샷 생성 -> (5)까지 확정된 ACTIVE 캠페인을 대상으로 가게와 캠페인의 조회 기능을 호출해 광고 서빙이 자기 테이블에 적재한다
  - (7) 사용자별 당일 이력(노출 횟수, 패스, 찜) 초기화
  - (8) 인메모리 캐시 잔액과 포인트 원장 대조
  - (3), (4), (5)의 작업 내용은 예산이, (6)은 광고 서빙이, (8)은 정산이 구현해 등록한다
  - (8) 대조를 정산이 맡는 이유는 대조가 정산의 포인트 원장과 광고 서빙의 노출 로그를 읽어야 하기 때문이다. 예산이 맡으면 예산이 두 도메인을 호출하게 되어 도메인 간 순환이 생긴다. 캐시 카운터는 예산이 단독으로 소유하므로 정산이 직접 고치지 않고, 재구성이 필요한 건만 예산에 통보해 예산이 자기 카운터를 고친다
  - 10:50: 찜 보유 사용자에게 오픈 알림 일괄 발송
  - 11:00: 모든 ACTIVE 캠페인 issue_open
  - 13:00: 인메모리 캐시 잔액과 포인트 원장 대조. 서빙 종료 직후라 처리 중인 건이 없어 정상 건을 불일치로 오판하지 않는다. (8)과 같은 작업이므로 정산이 구현해 등록한다
  - 서빙 시간대 10:05~12:55, 5분 간격: 잔액 부족으로 과금이 거부되는데 아직 ACTIVE인 캠페인을 예산이 찾아 중단을 다시 통보한다. 이미 PAUSED인 캠페인은 다시 통보받아도 상태가 달라지지 않는다. 예산이 구현해 등록한다
  - 캠페인별 사용 종료 시각(11:30~15:00 안, 30분 단위): 해당 캠페인 미사용 쿠폰 expire. 모든 시각은 관리자 설정값
  - 각 작업은 시작 시 배치 실행 이력에 기록하고, 이미 같은 영업일의 기록이 있으면 실행을 건너뛴다
- **예외:** 배치는 전용 서버 1대에서 실행하며, 모든 작업은 같은 날 두 번 실행되어도 결과가 달라지지 않아야 한다(멱등). 00:00 작업은 순서 의존이 있으므로 앞 작업이 실패하면 뒤 작업을 실행하지 않고 중단하며, 실패한 작업명과 사유를 기록해 관리자에게 알린다. 실패한 작업만 수동으로 재실행할 수 있다. 배치 실행 이력에 (작업명, 영업일) 단위 제약을 두어 배포나 재기동으로 인한 중복 실행을 차단하고, 실행 여부와 처리 건수를 조회할 수 있게 한다. 시각 설정 변경은 다음 날부터 적용

## 포인트 원장

### 노출 차감 및 원장 기록
- **우선순위:** 필수
- **설명:** 시스템이 유효 노출 판정 시 노출 단가만큼 점주 포인트를 차감하고 원장에 기록한다
- **입력:** serve_id, campaign_id, owner_id, 적용 단가, 잔액
- **선택:** 없음
- **상세:**
  - 인메모리 캐시의 원자 연산 하나로 (1) 당일 소진 + 단가 <= 하루 예산, (2) 잔액 >= 단가 두 조건을 함께 검사하고 둘 다 통과할 때만 차감한다. 검사와 차감이 한 연산이므로 동시 요청에서도 하루 예산과 잔액을 넘는 차감은 발생하지 않는다
  - 차감에 성공하면 PointDeductedEvent를 발행하고 정산이 이를 받아 관계형 DB의 포인트 원장에 DEDUCT를 기록한다. (serve_id, 원장 유형) UNIQUE 제약으로 멱등 처리한다
  - 이 이벤트는 별도 스레드로 넘기지 않고 같은 처리 흐름에서 동기로 처리해 원장 기록까지 끝낸 뒤 응답한다. 비동기로 넘기면 서버 재기동 시 차감만 남고 원장 기록이 사라진다
  - 사후 무효 판정 시 REFUND_INVALID
  - 두 조건 중 하나라도 불만족이면 차감하지 않고 미과금으로 판정한다. 과금 상태는 BILLED, NOT_BILLED_BUDGET(하루 예산 도달), NOT_BILLED_BALANCE(잔액 부족) 세 가지이며, 예산은 판정 결과를 호출한 쪽에 돌려줄 뿐 노출 로그에 직접 쓰지 않는다
  - 노출 로그 기록은 광고 서빙이 한다. 미과금 노출도 유효 노출이며 무효 노출로 분류하지 않는다
  - 초당 10,000건
  - 인메모리 캐시 잔액과 원장 합계 대조는 매일 13:00과 00:00 두 번 수행하며 정산이 구현해 등록한다. 13:00은 서빙 종료 직후라 처리 중인 건이 없어 정상 건을 불일치로 오판하지 않는다. 서빙 시간대(10:00~12:59) 중에는 대조하지 않는다
- **예외:** 하루 예산을 넘는 차감은 0건이어야 하고 잔액은 음수가 되지 않는다. 잔액이 노출 단가 미만이면 차감하지 않고 캠페인을 PAUSED(NO_POINTS)로 전이한다. 당일 소진이 하루 예산에 도달하면 상태 전이 없이 당일 노출만 중단한다. 이미 내려간 카드에서 오는 노출은 노출 인정 시간(30분) 안에 도착할 수 있으므로 중단 이후에도 미과금 노출이 발생한다. 이 노출은 점주에게 과금하지 않는다. 인메모리 캐시와 원장이 불일치하면 노출 로그를 근거로 원인을 가려 복구한다. 노출 로그에 대응하는 과금 건이 없으면 캐시가 어긋난 것이므로 원장 기준으로 캐시를 재구성한다. 노출 로그에 과금(BILLED)으로 기록됐는데 원장에 차감이 없으면 원장 기록이 누락된 것이므로 노출 로그를 근거로 원장에 차감을 보정 기록한다
