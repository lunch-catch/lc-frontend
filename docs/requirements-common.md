# 런치캐치 — 공통/시스템 요구사항 명세서

> 전체 시스템 공통 기능
> 기준 문서: 요구사항 명세서 V47 (2026-10-01 반영)

## 인증/인가

### 토큰 인증 및 역할 기반 접근 제어
- **우선순위:** 필수
- **설명:** 시스템이 접근 자격과 갱신 자격으로 요청자를 인증하고 역할별 기능 접근을 제어한다
- **입력:** Access Token, Refresh Token, 역할(SUPER_ADMIN/ADMIN/OWNER/USER)
- **선택:** 없음
- **상세:**
  - 단일 기준: Access Token은 JWT 30분.
  - Refresh Token은 Opaque Token으로 인메모리 캐시에 저장하고 SHA-256 해시를 관계형 DB에 백업하며, 관리자 1일, 점주 14일, 사용자 14일(자동 로그인 미체크 시 세션 쿠키).
  - 두 토큰은 HttpOnly, SameSite=Strict 쿠키로 전달하고 Rotation을 적용한다.
  - 로그아웃 시 Refresh Token을 폐기하고 Access Token valid-after cutoff를 저장한다. 프레임워크의 메서드 단위 인가로 API별 접근을 제어한다.
  - 역할별 로그인 행은 이 정책을 참조한다
- **예외:** 폐기된 Refresh Token을 사용하면 해당 계정의 전체 세션 로그아웃. 역할이 맞지 않으면 접근 거부(403)

## 캠페인 상태

### 캠페인 상태 전이
- **우선순위:** 필수
- **설명:** 시스템이 캠페인 상태(DRAFT/SCHEDULED/ACTIVE/PAUSED/ENDED)를 서버에서만 전이한다
- **입력:** 캠페인 ID, 현재 상태, 전이 상태, 전이 주체, PAUSED 사유(ADMIN/OWNER/NO_POINTS)
- **선택:** 사유
- **상세:**
  - 상태: DRAFT, SCHEDULED(자동 검수 통과, 시작 대기), ACTIVE, PAUSED, ENDED.
  - 허용 전이: DRAFT -> SCHEDULED(자동 검수 통과), SCHEDULED -> ACTIVE(집행 시작일 00:00 스케줄러, D-1 23:59까지 SCHEDULED인 건만), ACTIVE -> PAUSED(관리자/점주/포인트 부족), PAUSED -> ACTIVE, ACTIVE/PAUSED -> ENDED(집행 기간 종료, 새 캠페인 ACTIVE).
  - 당일 예산 소진과 수량 소진은 상태 전이 없이 당일 노출만 중단한다.
  - 낮에 일어난 전이(점주 중단과 재개, 관리자 중단, 충전 자동 재개, 종료)는 캠페인이 상태 변경 이벤트를 발행해 알리고, 광고 서빙이 받아 그날 후보 스냅샷의 서빙 상태를 바꿔 다음 피드 요청부터 반영한다("피드 구성 (배분 슬롯 배정)"). 광고 서빙이 이미 캠페인을 조회하고 있어 캠페인이 광고 서빙을 직접 호출하면 도메인 간 순환이 생기므로 이벤트로 알린다(도메인 간 의존 규칙 6). PAUSED -> ACTIVE로 재개되면 캠페인이 남은 예약액으로 남은 서빙 시간대의 목표 소진을 다시 계산한다(점주 "캠페인 수동 중단/재개"). 00:00에 이미 관리자 중단(ADMIN)이던 캠페인은 그날 예약이 없으므로("하루 시간표 스케줄러" (5) 예약 대상 아님) 재개돼도 다음 날 00:00 예약부터 노출한다. 낮에 중단됐다가 같은 날 재개되면 그날 남은 예약으로 노출한다. 모든 전이는 감사 로그로 기록한다
- **예외:** 허용되지 않은 캠페인 상태 전이 요청은 409 반환

## 피드 엔진

### 피드 구성 (배분 슬롯 배정)
- **우선순위:** 필수
- **설명:** 시스템이 공정성에 따라 배분 슬롯을 배정한다
- **입력:** 사용자 위치, 반경, 활성 캠페인 목록, 캠페인별 예산 소진 진행률, 사용자별 당일 노출/패스 이력, 차단 가게
- **선택:** 카테고리 필터
- **상세:**
  - 후보는 00:00 배치가 만든 그날의 피드 후보 스냅샷에서 찾는다. 스냅샷에는 그날 ACTIVE인 캠페인과, 그날 예약이 잡힌 PAUSED(OWNER, NO_POINTS) 캠페인이 서빙 불가 상태로 들어 있으며, 가게의 위치, 카테고리, 노출 대상 조건을 함께 담는다. 낮에 캠페인 상태가 바뀌면 캠페인이 발행한 상태 변경 이벤트를 받아 서빙 상태만 바꾼다("캠페인 상태 전이"). 서빙 중에는 다른 도메인의 테이블을 읽지 않는다. 후보 집합은 D-1 23:59까지 확정된 캠페인으로 고정되므로 하루 한 번 적재로 충분하다.
  - 후보 조건: 현재 시각이 서빙 시간대(10:00~12:59) 안, 스냅샷의 서빙 상태가 서빙 가능, 선착순 쿠폰 발급 잔여 수량 > 0(쿠폰이 소진 시점에 광고 서빙의 후보 갱신 기능을 호출하면 광고 서빙이 그날의 후보에서 제외한다. 발급 수는 쿠폰이 소유하므로 서빙 중에 쿠폰을 조회하지 않고, 후보 조건이 보는 것은 개수가 아니라 남았는지 여부이며 발급 취소가 없어 하루 안에서 되돌아오지 않는다), 사용자가 캠페인 노출 대상(점주 반경, 성별, 연령대 일치)에 해당하고 사용자 반경 내, 차단 가게 아님, 예산 소진 진행률 1.2 이하, 오늘 노출 횟수를 다 채우지 않음, 그날 이미 패스하지 않음.
  - 우선순위: 예산 소진 진행률 오름차순, 동률 시 등록 시각 오름차순. 신규 우선 노출(첫 3일) 캠페인은 진행률에 0.8을 곱해 앞순위로 당긴다.
  - 사용자 반경 내 후보 10개 미만이면 1->2->3->5km 확장(점주 반경 밖 사용자에게는 미노출).
  - 노출 대상을 좁게 정한 캠페인은 후보에 드는 횟수가 적어 진행률이 낮게 유지되므로 후보에 들 때는 자연히 앞순위가 된다(별도 보정 없음)
  - 예산 크기는 하루 노출 총량을 정하고 진행률은 노출 순서를 정한다. 예산이 큰 캠페인은 당일 예산을 늦게 소진해 후보에 더 오래 남으므로 결과적으로 더 많이 노출되지만, 같은 시점의 배정 순서를 앞당기지는 못한다. 노출되면 진행률이 올라가 뒤로 밀리고 노출되지 않는 동안 진행률이 내려가 다시 앞으로 오므로, 예산이 작은 캠페인이 큰 캠페인에 밀려 당일 예산을 남기는 일은 없어야 한다.
  - 하루가 시작되는 시점에는 모든 캠페인의 진행률이 0으로 같아 등록이 빠른 캠페인이 먼저 배정되지만, 노출이 시작되면 진행률이 갈라지므로 이 영향은 하루 첫 회차에 한정된다.
- **예외:** 배분 슬롯 후보 캠페인이 3개 미만이면 남는 슬롯을 관련성 슬롯으로 전환. 후보가 0개이면 피드 전체를 관련성 슬롯으로 구성

### 피드 구성 (관련성 정렬)
- **우선순위:** 필수
- **설명:** 시스템이 관련성 점수로 관련성 슬롯을 정렬한다
- **입력:** 거리, 카테고리, 할인 유형/값, 사용자 찜/패스 이력(30일), 필터
- **선택:** 없음
- **상세:**
  - 점수 = 거리 45% + 카테고리 선호도 35% + 할인 매력도 20% (시간 적합도는 오픈 시각 고정으로 삭제).
  - 거리 점수는 사용자와 가게가 가까울수록 1에 가깝고 사용자 반경 끝이면 0이다. 카테고리 선호도는 최근 30일 동안 그 카테고리 카드를 찜한 비율(찜 수 / (찜 수 + 패스 수))이며 기록이 5건 미만이면 중립값 0.5로 본다. 할인 매력도는 할인율을 0~1로 환산한 값이다.
  - 배분 슬롯에 이미 배정된 캠페인은 관련성 슬롯에 중복 배정하지 않고, 노출 횟수 상한도 동일하게 적용한다. 피드 구성 과정 디버그 로그(선택)
  - 관심 가게 등록은 관련성 점수에 반영하지 않는다. 카테고리 선호도와 신호가 중복되고, 관심 등록이 없는 신규 가게가 구조적으로 불리해지기 때문이다. 관심 가게에는 알림과 전용 목록으로 접근 경로를 제공한다.
- **예외:** 관련성 계산에 사용자 위치 이력은 사용하지 않고 현재 세션 위치만 사용. 점주 비용에 의한 순위 상승은 범위 밖

## 예산 소진 속도 조절

### 하루 예산 배분 및 예산 소진 진행률 계산
- **우선순위:** 필수
- **설명:** 시스템이 캠페인별 하루 예산을 시간대별로 나누고, 계획 대비 얼마나 썼는지를 나타내는 예산 소진 진행률을 계산한다
- **입력:** 캠페인 ID, 하루 예산, 당일 적용 단가, 집행 기간, 당일 누적 소진 포인트
- **선택:** 시간대 가중치 설정값
- **상세:**
  - 매일 00:00 하루 예산 초기화(미소진분 이월 없음. 점주가 바꾼 값이 예약돼 있으면 이때 적용한다. 점주 "하루 예산과 집행 기간 설정/변경 (등록 4단계)"), 일별 노출 목표 = 그날 적용 하루 예산 / 단가.
  - 그날 적용 하루 예산 = 그날 예약액 = min(점주가 설정한 하루 예산, 잔액). 매일 00:00에 정산이 이 금액을 점주 잔액에서 예약(원장 RESERVE)하고 캠페인에 넘긴다. 잔액이 설정값보다 적으면 그날은 잔액까지만 예약해 집행한다. 그날 예약 중 쓰지 않은 금액은 노출 인정 시간이 끝난 13:30에 잔액으로 되돌린다(원장 RELEASE, 이월 없음, "하루 시간표 스케줄러"). 예약액은 서빙 중에 바뀌지 않으며, 바뀌는 경우는 PAUSED(NO_POINTS) 캠페인의 충전뿐이다(점주 "포인트 결제"). 노출 단가보다 적으면 캠페인을 PAUSED(NO_POINTS)로 전이한다(점주 "잔액 부족 시 캠페인 게재 중단").
  - 점주당 활성 캠페인이 1건이고 활성 캠페인이 있는 동안 환불을 막으므로(점주 "포인트 환불 요청"), 예약은 그날 쓸 포인트를 다른 곳이 먼저 쓰는 일을 막기보다 캠페인이 잔액을 보관하지 않게 하는 데 목적이 있다.
  - 예산 소진 진행률 = 지금까지 실제로 쓴 포인트 / 지금까지 썼어야 할 포인트(그날 적용 하루 예산을 시간대 가중치로 나눈 계획값을 현재 시각까지 더한 값).
  - 예: 그날 적용 하루 예산 10,000포인트를 10시, 11시, 12시에 균등 배분하면 11시 30분까지 썼어야 할 포인트는 5,000이고, 실제 2,000을 썼으면 진행률은 0.4다. 값이 낮을수록 계획 대비 덜 쓴 것이라 배분 슬롯을 먼저 받는다. 금액이 아니라 비율이므로 예산이 큰 캠페인이 순서를 앞당기지 못한다.
  - 서빙 시간대 10:00~12:59, 시간대 가중치(그날 적용 하루 예산을 서빙 시간대별로 나누는 비율) 기본값 균등(10시 34%, 11시 33%, 12시 33%), 운영 데이터로 조정.
  - 당일 소진 실시간 카운터와 그날 예약액은 캠페인이 단독으로 소유한다. 다른 도메인은 자기 카운터를 만들지 않고 캠페인이 제공하는 조회 기능으로 읽는다. 당일 소진 카운터는 인메모리 캐시에 두고 원본은 정산의 포인트 원장이다.
  - **점주 잔액은 정산만 가진다.** 캠페인은 잔액을 보관하지도 조회하지도 않는다. 잔액은 정산의 00:00 예약과 충전 시 재예약, 점주 "잔액 및 내역 조회" 표시에만 쓰인다
- **예외:** 인메모리 캐시 장애 시 관계형 DB의 원장과 노출 로그로 카운터를 재구성한다. 당일 소진 재구성 값은 정산의 대조 작업("하루 시간표 스케줄러"의 (4)와 13:30)이 계산해 캠페인의 재구성 기능을 호출해 넘기고 캠페인이 자기 카운터에 반영한다. 장애 직후에는 그 작업을 수동으로 실행한다. 서빙 시간대 밖에는 피드 자체를 제공하지 않음. 캠페인의 당일 소진이 그날 적용 하루 예산에 도달하면 해당 캠페인의 당일 노출 중단

## 노출 수집

### 노출 이벤트 수집 및 검증
- **우선순위:** 필수
- **설명:** 시스템이 카드 표시 이벤트를 수신하여 유효/무효를 판정하고 저장한다.
- **입력:** serve_id, campaign_id, member_id, displayed_at, 반올림 좌표
- **선택:** viewed_ms(참고 지표)
- **상세:**
  - 노출 이벤트를 1건씩 받아 검증한다.
  - 검증은 두 가지뿐이다. (a) 인메모리 캐시의 serve 기록(키: serve_id, 유효 기간 = 노출 인정 시간 30분)이 존재하는지, 없으면 EXPIRED_OR_UNKNOWN. (b) serve 기록의 사용자와 요청 사용자가 같은지, 다르면 NOT_OWNER.
  - serve 기록은 광고 서빙이 피드를 내려줄 때 만든 자기 데이터이므로 다른 도메인을 조회하지 않는다. (serve_id, 요청 사용자) UNIQUE 제약으로 중복은 저장 거부. 요청 사용자를 키에 넣는 것은 다른 사용자가 같은 serve_id로 먼저 보낸 무효 노출이 원래 사용자의 유효 노출을 막지 못하게 하기 위해서다. 유효 노출은 serve 기록의 사용자만 만들 수 있으므로 serve당 유효 노출은 최대 1회다. 유효 판정 시 캠페인의 과금 가능 판정을 호출하고, 돌려받은 과금 상태를 노출 로그에 함께 기록한다. 단, 스냅샷에서 그 캠페인이 쿠폰 소진 상태이면 과금 가능 판정을 호출하지 않고 NOT_BILLED_SOLD_OUT으로 기록한다.
  - 초당 10,000건, p95 100ms. 좌표는 소수점 3자리로 반올림해 저장.
  - 유효/무효 결과를 202로 반환하되, 화면을 벗어나면서 보낸 요청은 클라이언트가 응답을 받지 못할 수 있으므로 응답에 의존하지 않는다. 향후 요청 수가 문제가 되면 여러 건을 묶어 받는 방식으로 전환할 수 있으며, 검증과 멱등 처리는 동일하다
- **예외:** 무효 노출도 사유와 함께 저장(삭제 없음)하되 포인트는 차감하지 않음. 유효 노출 중 그날 적용 하루 예산에 도달한 건, 캠페인 중단 이후나 쿠폰 소진 이후 도착한 건은 미과금으로 저장하며, 리포트에는 노출 수로 집계하되 과금액에는 반영하지 않는다

## 스케줄러

### 하루 시간표 스케줄러
- **우선순위:** 필수
- **설명:** 시스템이 00:00 활성화, 예산 초기화와 포인트 예약, 10:50 오픈 알림, 11:00 선착순 오픈, 캠페인별 사용 종료 시각 쿠폰 만료를 집행한다
- **입력:** 캠페인 ID, issue_id, 설정값(서빙 시간대, 오픈 시각, 사용 가능 시간, 알림 선행 시간)
- **선택:** 없음
- **상세:**
  - 00:00 작업은 다음 순서로 실행하며, 이 순서는 의존 관계이므로 임의로 바꿀 수 없다.
  - (1) 집행 기간이 끝난 캠페인 ENDED (잔여 포인트는 점주 잔액으로 유지)
  - (2) D-1 23:59까지 SCHEDULED인 캠페인 ACTIVE 전환 (기존 ACTIVE는 ENDED)
  - (3) 하루 예산 초기화 (전일 미소진분 이월 없음. 점주가 바꾼 값이 예약돼 있으면 이때 적용한다)
  - (4) 전일 당일 소진 캐시와 포인트 원장 대조 -> 원장 누락은 보정 기록하고 캐시 재구성이 필요한 건은 캠페인의 재구성 기능을 호출해 넘긴다
  - (5) 포인트 예약 -> 전날 13:30 해제가 실패해 남은 전일 예약이 있으면 먼저 잔액으로 되돌리고(RELEASE), 집행 기간 안의 ACTIVE, PAUSED(OWNER), PAUSED(NO_POINTS) 캠페인마다 min(설정 하루 예산, 잔액)을 예약(RESERVE)해 캠페인에 넘긴다("하루 예산 배분 및 예산 소진 진행률 계산"). 예약액이 0이어도 넘긴다. 남은 예약의 해제액을 원장의 차감 합계로 계산하므로 (4) 대조 뒤에 둔다
  - (6) 잔액 부족 판정(ACTIVE와 PAUSED(NO_POINTS)만 대상, PAUSED(OWNER)는 재개 요청 때 점주 "캠페인 수동 중단/재개" 규칙으로 판단). 예약액이 노출 단가보다 적은 ACTIVE 캠페인은 PAUSED(NO_POINTS)로, 단가 이상이 된 PAUSED(NO_POINTS) 캠페인은 ACTIVE로 되돌린다 (점주 "잔액 부족 시 캠페인 게재 중단")
  - (7) 시간대별 목표 소진 포인트 계산 -> (6)까지 확정된 ACTIVE 캠페인만 대상. 예약액이 분모이므로 (5) 뒤, 재개된 캠페인을 포함하도록 (6) 뒤에 둔다
  - (8) 그날의 피드 후보 스냅샷 생성 -> (6)까지 확정된 ACTIVE 캠페인은 서빙 가능으로, 그날 예약이 잡힌 PAUSED(OWNER, NO_POINTS) 캠페인은 서빙 불가로, 가게와 캠페인의 조회 기능을 호출해 광고 서빙이 자기 테이블에 적재한다("피드 구성 (배분 슬롯 배정)")
  - (9) 사용자별 당일 이력(노출 횟수, 패스, 찜) 초기화
  - (10) 가게별 반경 내 대상 인원 집계 -> 최근 7일 점심 접속 사용자를 가게마다 점주 반경 4단계 x 성별 x 연령대로 세어 캠페인에 넘긴다(점주 "하루 예산과 집행 기간 설정/변경 (등록 4단계)" 추천 입력). 앞 작업과 순서 의존이 없어 맨 뒤에 둔다
  - (3), (6), (7)의 작업 내용은 캠페인이, (4)와 (5)는 정산이, (8), (9), (10)은 광고 서빙이 구현해 등록한다(도메인 간 의존 규칙 4).
  - (4) 대조를 정산이 맡는 이유는 대조가 정산의 포인트 원장과 광고 서빙의 노출 로그를 읽어야 하기 때문이다. 캠페인이 맡으면 캠페인이 두 도메인을 호출하게 되어 도메인 간 순환이 생긴다. 당일 소진 캐시는 캠페인이 단독으로 소유하므로 정산이 직접 고치지 않고, 재구성이 필요한 건만 캠페인의 재구성 기능을 호출해 넘기고 캠페인이 자기 카운터를 고친다(도메인 간 의존 규칙 1, 6).
  - (5) 예약을 정산이 맡는 이유는 잔액이 정산의 원장에만 있기 때문이다. 정산이 예약액을 캠페인에 넘기는 방향은 정산이 이미 캠페인을 조회하는 방향과 같아 순환이 생기지 않는다.
  - 10:50: 알림 수신에 동의하고 당일 ACTIVE 캠페인을 찜했으며 FID가 등록된 사용자에게 오픈 알림 일괄 발송.
  - 11:00: 모든 ACTIVE 캠페인 issue_open.
  - 13:30: (a) 당일 소진 캐시와 포인트 원장 대조 (b) 쓰지 않은 예약을 잔액으로 해제(RELEASE = RESERVE - DEDUCT). 서빙이 12:59에 끝나도 이미 내려간 카드의 노출은 노출 인정 시간(30분) 동안 들어오므로, 그 시간이 끝난 13:30에 해야 처리 중인 차감이 없고 늦게 온 노출의 차감분도 해제액에서 빠진다. 해제액을 원장의 차감 합계로 계산하므로 (a) 대조 뒤에 (b) 해제를 둔다. 두 작업 모두 정산이 구현해 등록한다. 해제 뒤에 발견된 원장 누락(00:00 (4) 대조)은 이미 해제한 예약이 아니라 잔액에서 조정 기록으로 차감한다("노출 차감 및 원장 기록").
  - 캠페인별 사용 종료 시각(11:30~15:00 안, 30분 단위): 해당 캠페인 미사용 쿠폰 expire. 모든 시각은 관리자 설정값.
  - 각 작업은 시작 시 배치 실행 이력에 기록하고, 이미 같은 영업일의 기록이 있으면 실행을 건너뛴다
- **예외:** 배치는 전용 서버 1대에서 실행하며, 모든 작업은 같은 날 두 번 실행되어도 결과가 달라지지 않아야 한다(멱등). 00:00 작업은 순서 의존이 있으므로 앞 작업이 실패하면 뒤 작업을 실행하지 않고 중단하며, 실패한 작업명과 사유를 기록해 관리자에게 알린다. 실패한 작업만 수동으로 재실행할 수 있다. 배치 실행 이력에 (작업명, 영업일) 단위 제약을 두어 배포나 재기동으로 인한 중복 실행을 차단하고, 실행 여부와 처리 건수를 조회할 수 있게 한다. 시각 설정 변경은 다음 날부터 적용

## 포인트 원장

### 노출 차감 및 원장 기록
- **우선순위:** 필수
- **설명:** 시스템이 유효 노출 판정 시 노출 단가만큼 그날 예약된 포인트에서 차감하고 원장에 기록한다
- **입력:** serve_id, campaign_id, owner_id, 적용 단가, 그날 예약액
- **선택:** 없음
- **상세:**
  - 인메모리 캐시의 원자 연산 하나로 당일 소진 + 단가 <= 그날 적용 하루 예산을 검사하고, 통과할 때만 당일 소진을 늘린다. 검사와 차감이 한 연산이므로 동시 요청에서도 그날 적용 하루 예산을 넘는 차감은 발생하지 않는다. 그날 적용 하루 예산은 00:00에 잔액에서 예약한 금액이므로("하루 예산 배분 및 예산 소진 진행률 계산") 차감은 예약액 안에서만 일어나고 잔액을 건드리지 않는다.
  - 차감에 성공하면 PointDeductedEvent를 발행하고 정산이 이를 받아 관계형 DB의 포인트 원장에 DEDUCT를 기록한다. (serve_id, 원장 유형) UNIQUE 제약으로 멱등 처리한다. 이 이벤트는 별도 스레드로 넘기지 않고 같은 처리 흐름에서 동기로 처리해 원장 기록까지 끝낸 뒤 응답한다. 비동기로 넘기면 서버 재기동 시 차감만 남고 원장 기록이 사라진다. 사후 무효 판정 시 REFUND_INVALID.
  - 조건을 만족하지 못하면 차감하지 않고 미과금으로 판정한다. 과금 상태는 BILLED, NOT_BILLED_BUDGET(그날 적용 하루 예산 도달), NOT_BILLED_PAUSED(중단 이후 도착), NOT_BILLED_SOLD_OUT(쿠폰 소진 이후 도착, 판정 호출 없이 광고 서빙이 기록) 네 가지이며, 캠페인은 판정 결과를 호출한 쪽에 돌려줄 뿐 노출 로그에 직접 쓰지 않는다. 노출 로그 기록은 광고 서빙이 한다("노출 이벤트 수집 및 검증"). 미과금 노출도 유효 노출이며 무효 노출로 분류하지 않는다.
  - 초당 10,000건. 당일 소진 캐시와 원장 차감 합계 대조는 매일 13:30과 00:00 두 번 수행하며 정산이 구현해 등록한다("하루 시간표 스케줄러"). 13:30은 노출 인정 시간(30분)이 끝난 뒤라 처리 중인 차감이 없어 정상 건을 불일치로 오판하지 않는다. 대조 직후 쓰지 않은 예약을 해제한다. 서빙 시간대(10:00~12:59) 중에는 대조하지 않는다
- **예외:** 그날 적용 하루 예산을 넘는 차감은 0건이어야 하고 잔액은 음수가 되지 않는다. 당일 소진이 그날 적용 하루 예산에 도달하면 상태 전이 없이 당일 노출만 중단한다. 잔액 부족으로 인한 상태 전이는 서빙 중에 일어나지 않고 00:00 예약 직후와 충전으로 예약이 다시 잡힌 직후에만 판정한다(점주 "잔액 부족 시 캠페인 게재 중단"). 이미 내려간 카드에서 오는 노출은 노출 인정 시간(30분) 안에 도착할 수 있으므로 중단 이후에도 미과금 노출이 발생한다. 이 노출은 점주에게 과금하지 않는다. 인메모리 캐시와 원장이 불일치하면 노출 로그를 근거로 원인을 가려 복구한다. 노출 로그에 대응하는 과금 건이 없으면 당일 소진 캐시가 어긋난 것이므로 원장 기준으로 캐시를 재구성한다. 노출 로그에 과금(BILLED)으로 기록됐는데 원장에 차감이 없으면 원장 기록이 누락된 것이므로 노출 로그를 근거로 원장에 차감을 보정 기록한다. 두 경우를 구분하지 않고 원장 기준으로만 되돌리면 그 노출이 과금되지 않은 채 남아 정산 정합성 등식이 계속 깨진다. 두 복구 모두 대조 작업이 판정하며, 원장 보정은 정산이 자기 원장에 직접 쓴다. 13:30 예약 해제 뒤에 발견된 원장 누락은 해제한 예약이 아니라 점주 잔액에서 조정 기록으로 차감한다. 캐시 재구성은 캐시를 소유한 캠페인의 재구성 기능을 호출해 넘기고 캠페인이 자기 카운터를 고친다

## 부록: 도메인 간 의존 규칙

기능 명세 본문에서 "도메인 간 의존 규칙 N"으로 참조하는 규칙이다.

- **규칙 1:** 각 도메인은 자기 애그리거트만 직접 읽고 쓴다. 다른 도메인의 데이터는 그 도메인이 공개한 기능으로만 다룬다
- **규칙 2:** 분석은 전환 퍼널 이벤트 로그와 자기 집계 테이블만 읽는다. 일별 집계 배치는 예외로 다른 도메인 데이터를 읽을 수 있으며, 조회 기능은 집계 결과만 읽는다
- **규칙 3:** 운영은 다른 도메인과 같은 층이 아니라 아래에서 떠받치는 설정 제공 모듈이다. 운영은 어떤 도메인도 의존하지 않고, 모든 도메인이 운영의 설정값을 읽는다
- **규칙 4:** 스케줄러는 실행 순서와 멱등만 책임진다. 각 작업의 내용은 해당 도메인이 구현해 등록하며, 앞 작업이 실패하면 뒤 작업을 실행하지 않는다
- **규칙 5:** 인증과 인가는 모든 도메인이 직접 가져다 쓰는 공용 인증 모듈이다. 다른 도메인은 자기만의 권한 체크를 따로 만들지 않고 이것만 쓴다. 이 모듈을 바꾸면 전 도메인이 영향을 받으므로 변경은 팀 합의로 한다. 세션 정책은 "토큰 인증 및 역할 기반 접근 제어" 행이 단일 기준이다
- **규칙 6:** 도메인 간 의존은 순환 없이 한 방향으로 둔다. 의존하는 도메인은 상대가 공개한 기능을 직접 호출해 읽거나 쓰고, 의존받는 도메인은 자기 이벤트를 발행해 알린다. 새 의존은 순환이 생기지 않는 방향으로 정한다
