# 런치캐치 — 사용자(직장인) 기능 요구사항 명세서

> FE-사용자 담당: 서지현
> 기준 문서: 요구사항 명세서 V47 (2026-10-01 반영)

## 회원

### 카카오 소셜 로그인/가입
- **우선순위:** 필수
- **설명:** 카카오 계정으로 가입하고 로그인한다
- **입력:** 카카오 ID 토큰, provider_user_id(kakao_id), 닉네임
- **선택:** 프로필 이미지
- **상세:**
  - 카카오 OIDC 인증 후 카카오 회원번호(provider_user_id)를 사용자 식별자로 사용(탈퇴 후 재가입 시에도 동일). 카카오에서 성별과 연령 정보는 받지 않는다(비즈앱 검수 필요).
  - 닉네임과 프로필 이미지는 최초 가입 시에만 동기화, 이후 사용자가 수정. 닉네임 중복 제한 없음. 기기 식별자는 수집하지 않는다.
  - 토큰 정책은 공통 "토큰 인증 및 역할 기반 접근 제어" 행을 따른다. 가입 직후 온보딩 폼으로 이동
- **예외:** 카카오 인가 코드 검증에 실패하면 401. 정지된 계정(provider_user_id 기준)의 재가입은 거부

### 온보딩 폼 입력
- **우선순위:** 필수
- **설명:** 사용자가 가입 직후 동의 항목과 맞춤 노출용 정보(성별, 연령대)를 입력한다
- **입력:** 위치정보 수집 동의, 광고성 알림 수신 동의, 성별(남/여/기타), 연령대(20대/30대/40대/50대 이상)
- **선택:** 없음
- **상세:**
  - 위치정보 동의와 광고성 알림 동의는 각각 별도 체크박스로 받는다.
  - 성별과 연령대는 맞춤 쿠폰 노출에 필요한 필수 입력 항목이며, "맞춤 쿠폰 노출을 위해 사용"을 화면에 고지한다. 성별은 남, 여, 기타 중에서 고르게 하여 선택지를 제한하지 않는다.
  - 가입 진행중 상태를 두고 온보딩이 끝나지 않으면 다음 로그인 시 온보딩으로 리다이렉트한다
- **예외:** 성별 또는 연령대를 입력하지 않으면 온보딩을 완료할 수 없고 피드를 이용할 수 없다. 위치정보 동의를 거부하면 피드와 지도 이용 불가를 안내한다(가입은 가능)

### 자동 로그인 / 토큰 재발급
- **우선순위:** 필수
- **설명:** 사용자의 자동 로그인 선택 여부에 따라 시스템이 로그인 상태를 유지하고, 세션이 만료되면 갱신한다
- **입력:** Refresh Token
- **선택:** 없음
- **상세:**
  - 자동 로그인 체크 시 Refresh Token 14일, 미체크 시 브라우저 종료와 함께 만료(세션 쿠키).
  - Access Token 만료 시 Refresh Token으로 재발급하며 카카오 재인증은 필요 없다. Rotation을 적용해 한 번 쓴 Refresh Token은 재사용할 수 없다.
  - 만료 시간과 저장 방식은 공통 인증 행이 단일 기준
- **예외:** 갱신 자격이 만료되거나 폐기되면 사용자는 재로그인. 폐기된 갱신 자격을 다시 쓰면 해당 사용자의 모든 세션 종료

### 로그아웃
- **우선순위:** 필수
- **설명:** 사용자가 로그아웃하면 시스템이 세션을 종료한다
- **입력:** 없음
- **선택:** 없음
- **상세:**
  - 서비스 세션을 폐기하고 카카오 측 로그아웃도 함께 요청한다. 카카오 계정 자체를 로그아웃시키는 기능은 구현하지 않는다
- **예외:** 사용자가 로그인 상태가 아니면 로그아웃 실패

## 위치

### 위치 설정
- **우선순위:** 필수
- **설명:** 사용자가 지도 서비스 이용을 위해 현재 위치를 설정한다
- **입력:** 위치(위도/경도) 또는 주소
- **선택:** 위치 별명(직장 등)
- **상세:**
  - 위치 동의 시 GPS로 현재 위치 감지 후 "이 위치를 저장할까요?" 확인. 동의 거부 시 도로명 주소 검색으로 직접 입력. 저장된 위치를 기준으로 피드/지도 노출.
  - 저장 위치는 사용자가 삭제할 때까지 보관하며 이동 이력은 저장하지 않음. 노출 로그에는 소수점 3자리 반올림 좌표만 기록
- **예외:** GPS 위치 감지에 실패하면 주소 검색으로 전환하도록 안내

## 쿠폰 광고 피드

### 스와이프 피드 조회
- **우선순위:** 필수
- **설명:** 사용자가 서빙 시간대(10:00~12:59)에 현재 위치 기준으로 구성된 쿠폰 카드 피드를 본다. 피드에서는 찜과 패스만 가능하고 발급은 하지 않는다
- **입력:** 현재 위치(위도/경도)
- **선택:** 필터 설정
- **상세:**
  - 서버가 10장 단위로 피드 구성: 배분 슬롯 3장(1, 4, 7번 위치) + 관련성 슬롯 7장.
  - 각 카드에 serve_id와 served_at을 부여하고 serve 기록을 인메모리 캐시(TTL 30분)와 관계형 DB 서빙 로그에 저장한다. 응답 p95 300ms.
  - 피드 요청 위치는 (영업일, 사용자)마다 그날 첫 요청 하나만 소수점 3자리로 반올림해 일별 접속 위치로 남기고 8일 뒤 지운다. 점주 "하루 예산과 집행 기간 설정/변경 (등록 4단계)" 추천 인원 집계(공통 "하루 시간표 스케줄러" (10)단계)에만 쓴다. 서빙 로그와 같이 응답 뒤에 비동기로 저장한다.
  - 클라이언트는 서버가 준 순서를 변경 불가. 각 카드에 "광고" 라벨 표시 필수(전부 광고여도 표시광고법상 표시 의무는 유지). 쿠폰 할인 조건, 캠페인별 사용 시간, 수량 제한을 카드에서 확인 가능.
  - 피드 카드에 발급 버튼 없음(발급은 찜 목록에서). 카드에 "11:00 오픈"과 캠페인별 사용 시간(예: 12:00~14:00) 표시. 카드 탭 시 가게 상세 페이지로 이동.
  - 상단 현재 위치 영역 탭 시 위치 변경 가능(GPS 재감지 또는 주소 검색)
- **예외:** 서빙 시간대 밖(13:00~익일 09:59)의 피드 요청에는 카드 없이 "내일 10시에 만나요" 안내만 반환(노출 없음). 피드 API는 사용자 ID 기준 분당 2회로 제한하며 초과 요청은 429로 거부한다. 공용 네트워크를 고려해 IP 기준 제한은 두지 않는다. 사용자 반경 1km 안의 후보 캠페인이 10개 미만이면 반경을 2 -> 3 -> 5km로 확장하되 점주 반경 밖의 사용자에게는 노출하지 않음. 후보 캠페인이 없으면 빈 피드 안내. 위치 획득에 실패하면 마지막 수동 입력 위치 사용

### 스와이프 찜/패스
- **우선순위:** 필수
- **설명:** 사용자가 본 카드를 우측(찜: 선착순 이벤트 참여 의사) 또는 좌측(패스)으로 스와이프하여 참여 여부를 정한다
- **입력:** serve_id, 캠페인 ID, 행위(wish/pass), 발생 시각
- **선택:** 없음
- **상세:**
  - 노출은 카드가 화면에 보인 순간 이미 집계되므로, 사용자가 카드를 어느 쪽으로 넘기든(찜이든 패스든) 노출 수와 점주의 과금은 달라지지 않는다.
  - 찜 시 찜 목록에 추가되고 매일 11:00 선착순 오픈에 참여 자격을 얻는다(11:00 이후 찜은 찜 목록에서 즉시 발급 요청 가능). 피드에서는 찜/패스 외 다른 행위 없음.
  - 패스 시 당일 재노출 제외. 각 행위는 wish/pass 이벤트로 로깅되어 관련성 학습에 사용. 찜한 캠페인은 피드에 재노출하지 않으며 찜 목록에서만 접근
- **예외:** 같은 사용자가 보낸 동일 serve_id의 중복 스와이프는 최초 1건만 반영. 다른 사용자가 그 serve_id로 보낸 스와이프는 보낸 사용자의 기록으로만 남아 원래 사용자의 스와이프를 막지 않는다. 한 세션 안에서 동일 캠페인은 1회만 노출

### 노출 수 집계
- **우선순위:** 필수
- **설명:** 시스템이 쿠폰 피드에서 카드가 사용자 화면에 표시되는 시점에 노출 1회로 기록한다
- **입력:** serve_id, 캠페인 ID, displayed_at(표시 시각)
- **선택:** 없음
- **상세:**
  - 카드가 스와이프 피드의 맨 위 카드로 화면에 표시되는 순간 노출 1회로 카운트한다. 뷰포트 비율과 스와이프 방향은 판정에 사용하지 않는다.
  - 서버가 내려준 카드라도 사용자가 그 카드까지 넘기지 않았으면 노출이 아니다. 하나의 serve_id에 대해 노출은 최대 1회.
  - 노출 이벤트는 카드가 표시되는 시점마다 1건씩 즉시 전송한다.
  - 화면을 벗어나는 순간(다른 앱 전환, 탭 닫기, 피드 화면 이탈)에 발생한 이벤트도 전송이 완료되도록 요청에 keepalive 옵션을 사용한다.
  - 전송에 실패하면 1회 재시도하고, 그래도 실패하면 그 노출은 집계하지 않는다(집계되지 않은 노출은 차감도 되지 않으므로 점주에게 불리하지 않다)
  - 하루 예산에 도달한 뒤, 캠페인 중단 뒤, 쿠폰 소진 뒤 도착한 노출도 노출 수로는 집계하되 과금하지 않는다(공통 "노출 차감 및 원장 기록")
- **예외:** 같은 사용자가 보낸 동일 serve_id의 중복 전송은 DB UNIQUE 제약으로 1건만 저장(공통 "노출 이벤트 수집 및 검증"). 앱이 백그라운드로 전환된 동안의 카드는 표시로 보지 않음. served_at 대비 노출 인정 시간(30분)을 넘겨 도착한 노출 이벤트는 EXPIRED_OR_UNKNOWN 무효

### 필터 설정
- **우선순위:** 필수
- **설명:** 사용자가 피드에 적용할 필터를 설정하고 저장한다
- **입력:** 카테고리(복수), 정렬(거리순/할인율순)
- **선택:** 없음
- **상세:**
  - 사용자가 설정한 필터(카테고리, 정렬)는 계정에 저장되어 다시 접속해도 유지된다. 피드 10장 중 관련성 슬롯 7장에는 필터를 모두 적용한다.
  - 배분 슬롯 3장은 점주에게 노출 기회를 공정하게 나누는 자리이므로, 사용자가 고른 카테고리 안에서만 뽑되 순서는 사용자의 정렬 기준이 아니라 공정성(예산 대비 덜 노출된 캠페인 우선)으로 정한다
- **예외:** 사용자가 카테고리를 전체 해제하면 전체 카테고리 선택으로 간주

### 가게 추천 차단
- **우선순위:** 권장
- **설명:** 사용자가 특정 가게의 캠페인을 앞으로 피드에서 받지 않도록 차단한다
- **입력:** 가게 ID
- **선택:** 없음
- **상세:**
  - 카드 길게 누르기로 진입. 차단 시 해당 가게의 모든 캠페인이 피드 후보에서 제외. 차단 이력은 관련성 학습에 반영. 마이페이지에서 차단 목록 조회 및 해제 가능
- **예외:** 차단한 가게의 이미 찜한 쿠폰은 찜 목록에 유지되며 사용자에게 별도 안내

## 탐색 (홈)

### 가게 목록 조회 (리스트/지도 토글)
- **우선순위:** 필수
- **설명:** 사용자가 현재 위치 기준 주변 입점 가게를 리스트 또는 지도로 조회한다
- **입력:** 현재 위치
- **선택:** 카테고리, 거리, 정렬
- **상세:**
  - 리스트 뷰 / 지도 뷰 전환 토글 제공.
  - 리스트 뷰: 활성 캠페인 보유 가게 상단 노출, 가게명, 카테고리, 거리, 할인 정보 표시.
  - 지도 뷰: 네이버/카카오 지도 API 연동, 캠페인 보유 가게는 구분 마커로 표시, 핀 선택 시 가게 상세 페이지로 이동, 현재 위치 새로고침 버튼 제공, 반경 확장은 사용자 반경 내 후보가 10개 미만일 때 1 -> 2 -> 3 -> 5km로 넓히되 점주 반경 밖 사용자에게는 노출하지 않는 규칙을 적용, 지도에 핀이 보이는 것은 광고 노출로 세지 않고 map_view 이벤트로만 기록한다.
  - 리스트와 지도 모두 선택 시 가게 상세 페이지로 이동. 상단 현재 위치 영역 탭 시 위치 변경 가능(GPS 재감지 또는 주소 검색)
  - 활성 캠페인 유무와 할인 요약은 가게가 자기 테이블에 둔 그날의 캠페인 요약에서 읽는다. 캠페인이 상태를 바꿀 때마다(00:00 종료와 활성 전환, 재개, 잔액 부족 중단) 가게가 공개한 요약 갱신 기능을 호출해 값을 넘기고, 가게가 자기 요약을 갱신한다. 가게가 캠페인을 직접 조회하면 캠페인이 이미 가게를 조회하고 있어 도메인 간 순환이 생긴다. 요약에는 가게 ID, 캠페인 ID, 상태, 할인 내용, 캠페인별 사용 시간이 들어간다. 요약이 가게 테이블에 있으므로 활성 캠페인 보유 가게를 상단에 올리는 정렬과 페이지네이션을 서버에서 한 번에 처리한다
- **예외:** 주변 입점 가게가 0건이면 빈 상태 안내. 사용자가 위치 권한을 거부하면 수동 위치 입력 안내

### 가게 검색
- **우선순위:** 필수
- **설명:** 사용자가 가게명, 메뉴명으로 입점 가게를 검색한다
- **입력:** 검색어
- **선택:** 카테고리 필터, 거리 필터
- **상세:**
  - 검색 결과 리스트로 표시. 가게명, 카테고리, 거리, 활성 캠페인 유무 표시. 선택 시 가게 상세 페이지로 이동. 활성 캠페인 유무는 "가게 목록 조회 (리스트/지도 토글)"과 같은 요약에서 읽는다
- **예외:** 검색 결과가 0건이면 빈 상태 안내

### 가게 상세 조회
- **우선순위:** 필수
- **설명:** 사용자가 가게 상세 정보를 확인하고 캠페인을 찜하거나 쿠폰을 발급받는다
- **입력:** 가게 ID
- **선택:** 없음
- **상세:**
  - 상호명, 업종, 주소, 전화번호, 영업시간, 가게 대표 이미지, 가게 내부 이미지, 대표 메뉴 목록(메뉴 이미지, 메뉴명, 메뉴 상세설명, 메뉴 가격)을 표시한다. 위치 지도 미리보기. 관심 가게 등록/해제 버튼.
  - 저장된 포스터 HTML을 iframe으로 렌더링해 보여준다. 현재 활성 캠페인이 있으면 캠페인 정보(할인 내용, 11:00 오픈, 캠페인별 사용 시간, 잔여 수량) 표시.
  - 찜 전이면 "찜해두기" 버튼, 찜한 뒤 11:00 이후면 "받기" 버튼(찜 목록과 동일 발급 API), 이미 찜한 캠페인은 "찜 취소" 버튼.
  - 피드가 아닌 상세 화면이므로 노출로 카운트하지 않고 poster_open 이벤트만 로깅. 스와이프 카드 탭, 찜 목록, 지도 핀, 관심 가게 알림에서 진입 가능
  - (프론트에서 상세 페이지 상단에 쿠폰 활성화 또는 비활성화 버튼 배치.)
  - 이 화면이 쓰는 데이터는 소유가 넷으로 갈리므로 읽는 방법도 갈린다.
  - (1) 상호, 업종, 주소, 영업시간, 이미지, 메뉴는 가게 자기 데이터다.
  - (2) 할인 내용과 캠페인별 사용 시간은 "가게 목록 조회 (리스트/지도 토글)"과 같은 그날의 캠페인 요약에서 읽는다.
  - (3) 저장된 포스터 HTML은 가게가 포스터의 조회 기능으로 읽는다. 포스터는 어떤 도메인도 호출하지 않으므로 이 방향에 순환이 없다.
  - (4) 잔여 수량, 관심 가게 등록 여부, 찜 여부는 클라이언트가 각각 쿠폰과 사용자와 광고 서빙의 조회 기능을 불러 화면에서 합친다. 실시간이거나 사용자별이라 요약으로 만들 수 없고, 가게가 서버에서 합치면 순환이 넷 생긴다.
  - 상세 화면은 성능 목표가 걸린 API가 아니므로(비기능 명세서의 피드 API 응답 시간 목표는 "스와이프 피드 조회"의 피드에 걸린 것) 호출이 나뉘는 대가를 감수한다
- **예외:** 종료된 캠페인은 "종료된 이벤트입니다" 안내. 비활성 가게는 접근 불가 안내. 쿠폰 수량이 소진되면 "마감" 안내. 쿠폰 일 3개 초과 발급 시 거절 사유 표시

## 찜 목록

### 찜한 캠페인 조회
- **우선순위:** 필수
- **설명:** 사용자가 찜한 캠페인을 목록으로 확인하고 11:00 오픈 이후 여기서 쿠폰을 발급받는다
- **입력:** 없음
- **선택:** 없음
- **상세:**
  - 11:00 오픈 전에는 "11:00 오픈" 카운트다운과 잔여 수량, 캠페인별 사용 시간, 상태(발급 전) 표시. 오픈 후에는 "받기" 버튼 활성화(발급 가능/마감). 발급은 이 화면에서만 일어난다.
  - 하루 발급 가능 잔여 횟수 표시(최대 3개). 찜 목록 조회는 광고 노출로 세지 않고 wishlist_view 이벤트로만 기록한다.
  - 이 화면은 두 도메인의 조회 기능을 클라이언트가 각각 호출해 합친다. 광고 서빙은 찜 목록만 돌려주고, 잔여 수량과 캠페인별 사용 시간과 발급 가능 여부와 하루 발급 잔여 횟수는 쿠폰이 한 번에 돌려준다(쿠폰이 캠페인의 조회 기능으로 정원과 사용 시간을 읽는다). 광고 서빙이 서버에서 합치면 광고 서빙이 쿠폰을 호출하게 되는데, 쿠폰은 발급 자격 확인을 위해 이미 광고 서빙의 찜 여부를 읽고 있어("선착순 쿠폰 발급") 도메인 간 순환이 생긴다. 대가로 11:00 직전 피크에 이 화면의 조회 요청이 두 번으로 늘어나므로 부하 산정에 반영한다.
  - 클라이언트는 찜 목록 조회에서 받은 캠페인 ID를 쿠폰 조회에 함께 보낸다. 쿠폰이 찜 목록을 다시 읽으면 클라이언트가 이미 들고 있는 데이터를 한 번 더 읽는 것이고, 그 자리가 11:00 직전 피크다. 쿠폰이 찜 여부를 직접 확인하는 것은 실제 발급 시점뿐이다("선착순 쿠폰 발급")
- **예외:** 종료된 캠페인은 찜 목록에서 자동 제거. 찜 목록이 0건이면 빈 상태 화면과 피드 이동 버튼 표시

### 찜한 캠페인 삭제
- **우선순위:** 필수
- **설명:** 사용자가 찜한 캠페인을 목록에서 삭제한다
- **입력:** 캠페인 ID
- **선택:** 없음
- **상세:**
  - 삭제한 캠페인은 당일 피드에 재노출되지 않음. 삭제한 캠페인은 10:50 선착순 오픈 알림 대상에서도 제외된다. 알림은 10:50에 찜 목록을 조회해 발송하므로("선착순 오픈 알림") 따로 취소할 예약이 없다. 알림 취소를 광고 서빙이 알림에 요청하는 형태로 구현하면 알림이 이미 광고 서빙의 찜 목록을 읽고 있어 도메인 간 순환이 생긴다
- **예외:** 없음

## 알림

### 선착순 오픈 알림
- **우선순위:** 필수
- **설명:** 사용자가 매일 10:50(오픈 10분 전)에 알림 수신에 동의하고 찜한 캠페인이 당일 ACTIVE 상태이면 Web Push 알림을 받는다
- **입력:** 캠페인 ID, 사용자 ID, Firebase Installation ID(FID)
- **선택:** 없음
- **상세:**
  - 알림 수신 동의자 중 찜 목록에 당일 ACTIVE 캠페인이 있으면서 FID가 등록된 사용자를 10:50 시점의 최신 상태를 기준으로 조회하여 일괄 발송한다. FID를 서버에 최초 등록하거나 다시 동기화할 때 마지막 동기화 시각(last_synced_at)을 갱신하며, 발송 대상별 FID를 이용해 개별 대상으로 Web Push를 전송한다.
  - 발송 대상은 500명 단위로 나누어 순차적으로 처리하며, 각 단위의 알림 및 발송 대기 데이터는 여러 건을 묶어 한 번에 저장한다.
  - FCM 발송 성공 시, notification_sent 이벤트 로깅. FCM 발송 실패 시, 시도 횟수와 오류 원인 로깅.
  - 알림 발송은 광고 노출로 세지 않으므로 점주 포인트가 차감되지 않는다
- **예외:** 알림 미동의 사용자, FID가 등록되지 않은 사용자는 발송 대상에서 제외. FID 등록 또는 재동기화에 실패한 경우 last_synced_at을 갱신하지 않음. 일시적 오류로 발송에 실패한 대상만 재시도하며, 이미 발송에 성공한 대상은 재발송 대상에서 제외. 재시도 한도(2회) 초과 시, FAILED 처리. 11:00 이후 미발송 건은 EXPIRED 처리. FCM 응답으로 온 등록 정보가 만료·해제 등 사용 불가능한 것으로 확인되면 해당 FID 등록 정보 삭제 후, 추가 발송 및 재시도 중단. 같은 사용자에게 같은 캠페인의 같은 알림이 두 번 가지 않도록 (사용자, 캠페인, 날짜, 알림 유형) 단위로 중복 발송을 차단

### 관심 가게 신규 캠페인 알림
- **우선순위:** 권장
- **설명:** 사용자가 관심 등록한 가게가 새 캠페인을 등록하면 알림을 받는다
- **입력:** 가게 ID, 캠페인 ID
- **선택:** 없음
- **상세:**
  - 캠페인 ACTIVE 전환 시 해당 가게의 관심 등록 사용자에게 발송. 사용자-캠페인별 1회만 발송. notification_sent 이벤트 로깅
- **예외:** 알림에 동의하지 않았거나 관심 등록을 해제한 사용자에게는 미발송. 캠페인이 취소되면 예약 알림 취소

### 관심 가게 발급 임박 알림
- **우선순위:** 권장
- **설명:** 사용자가 관심 등록한 가게의 당일 캠페인에 대해 10:50 오픈 알림을 받는다
- **입력:** 캠페인 ID, 발송 시각
- **선택:** 없음
- **상세:**
  - 알림 동의자에 한해 10:50 일괄 발송. 사용자-캠페인별 1회만 발송. notification_sent 이벤트 로깅
- **예외:** 알림에 동의하지 않았거나 관심 등록을 해제한 사용자에게는 미발송. 캠페인이 종료되면 예약 알림 취소

### 알림 목록 조회
- **우선순위:** 필수
- **설명:** 사용자가 수신한 알림 목록을 조회한다
- **입력:** 없음
- **선택:** 없음
- **상세:**
  - 사용자가 수신한 선착순 오픈 알림 목록을 최신순으로 조회.
  - 각 알림은 읽음/안읽음 상태로 구분하며, 개별 읽음 처리와 전체 읽음 처리 지원.
  - read_at이 NULL이면 안읽음, 값이 존재하면 읽음으로 판단
- **예외:** 수신한 알림이 없으면 빈 목록 반환

## 쿠폰

### 선착순 쿠폰 발급
- **우선순위:** 필수
- **설명:** 사용자가 11:00 오픈 이후 찜 목록에서 찜한 캠페인의 쿠폰을 선착순으로 발급받는다
- **입력:** 캠페인 ID, serve_id, 요청 시각
- **선택:** 없음
- **상세:**
  - 11:00에 스케줄러가 그날 ACTIVE인 모든 캠페인에 issue_open 이벤트를 생성한다. 찜한 사용자만 찜 목록에서 요청 가능(피드에서는 불가).
  - 인메모리 캐시의 원자 연산으로 순번을 확정한 뒤 관계형 DB에 발급을 기록한다. 하루 최대 3개, 동일 캠페인 중복 발급 불가((event_id, 사용자) UNIQUE 제약. event_id는 11:00에 캠페인마다 하루 하나 생성되는 issue_open의 식별자).
  - 11:00에 전체 캠페인이 동시에 열리므로 전체 합산 10,000건을 10초 내 처리하고 캠페인별 초과 발급 0건. issue 이벤트 로깅.
  - 마지막 한 장을 발급해 잔여 수량이 0이 되는 그 한 번만 광고 서빙이 공개한 후보 갱신 기능을 호출해 소진을 넘기고, 광고 서빙이 그날의 피드 후보에서 해당 캠페인을 뺀다(공통 "피드 구성 (배분 슬롯 배정)"). 발급 트랜잭션 안에서 함께 처리한다. 유실되면 소진된 캠페인이 하루 종일 피드에 남고 그 노출은 과금되기 때문이다. 이 호출이 실패해 마지막 한 장의 발급이 롤백되는 것은 캠페인당 하루 한 번 있을까 말까 한 자리이고 방향이 과발급이 아닌 미발급이다. 캠페인당 하루 한 번이므로 11:00 피크의 처리량 목표에 영향을 주지 않는다
- **예외:** 오픈 전 발급 요청, 찜하지 않은 사용자의 발급 요청, 쿠폰 수량 소진, 쿠폰 일 3개 초과 발급, 정지된 계정의 요청은 사유 코드와 함께 거부. 인메모리 캐시 장애 시 관계형 DB의 발급 기록을 기준으로 카운터를 복구

### 쿠폰함 조회
- **우선순위:** 필수
- **설명:** 사용자가 발급받은 쿠폰을 조회한다
- **입력:** 없음
- **선택:** 상태 필터
- **상세:**
  - 상태: 사용가능, 사용완료, 만료. 발급일, 만료일, 사용 조건(할인 대상, 할인 유형/값, 캠페인별 사용 가능 시간) 표시. 사용가능 쿠폰에 "QR 보기" 버튼
- **예외:** 발급받은 쿠폰이 0건이면 빈 상태 화면

### 동적 QR 생성
- **우선순위:** 필수
- **설명:** 사용자가 발급받은 쿠폰의 1회용 동적 QR을 생성한다
- **입력:** issue_id, 만료 시각, jti, 서버 서명
- **선택:** 없음
- **상세:**
  - 60초마다 갱신되는 서버 서명 토큰(JWT). 1회 사용 후 jti를 인메모리 캐시에 기록하여 재사용을 차단한다. 사용 가능 시간은 캠페인별(11:30~15:00 안에서 점주 선택)이며 종료 시각에 스케줄러가 만료 처리(expire 이벤트)
- **예외:** 쿠폰 사용 시작 시각 전에는 QR 대신 "HH:MM부터 사용 가능" 표시. 만료되었거나 이미 사용된 쿠폰은 QR 생성 불가. 오프라인 상태에서는 마지막 QR의 남은 유효 시간만 표시

### 쿠폰 사용 내역 조회
- **우선순위:** 필수
- **설명:** 사용자가 쿠폰 사용 이력을 확인한다
- **입력:** 없음
- **선택:** 기간 필터
- **상세:**
  - 사용완료/만료 구분 표시, 총 사용 횟수. 날짜별 그룹핑, 시간 내림차순
- **예외:** 쿠폰 사용 내역이 0건이면 빈 상태 화면

## 부록: 알림 발송 상태 정의 (NotificationDeliveryStatus)

| 상태코드 | 한글명 | 설명 | 진입 조건 | 사용자 가능 액션 | 관리자 가능 액션 | 다음 상태 |
|---|---|---|---|---|---|---|
| PENDING | 발송 대기 | 알림 발송 대상으로 선정되어 발송 준비가 완료되었지만 아직 FCM Web Push 발송을 시작하지 않은 상태 | 10:50 시점에 알림 수신에 동의하고, 당일 ACTIVE 캠페인을 찜했으며, 해당 사용자에게 FID가 등록되어 있어 발송 대상으로 선정된 경우 | - | - | PROCESSING / EXPIRED |
| PROCESSING | 발송 처리 중 | Notification Worker가 최초 발송을 기다리는 데이터 또는 재시도를 기다리는 데이터를 가져와 FCM Web Push 발송을 진행 중인 상태 | Notification Worker가 PENDING 또는 RETRY 상태의 발송 작업을 가져와 처리를 시작한 경우 | - | - | SENT / RETRY / FAILED / EXPIRED |
| SENT | 발송 성공 | FCM을 통한 Web Push 발송 요청이 정상적으로 처리된 상태 | FCM 발송 요청에 대한 성공 응답을 수신한 경우 | 알림 목록 조회, 읽음 처리 | - | - |
| RETRY | 재시도 대기 | 일시적인 오류로 발송에 실패하여 재시도를 기다리는 상태 | 네트워크 오류, Timeout, FCM 일시 장애 등 일시적인 발송 오류가 발생한 경우 | - | - | PROCESSING / EXPIRED |
| FAILED | 발송 실패 | 재시도 한도인 2회 내 알림 발송을 완료하지 못해 최종적으로 발송에 실패한 상태 | 재시도 2회 후에도 FCM 발송에 실패한 경우 | - | - | - |
| EXPIRED | 발송 만료 | 캠페인 오픈 시각(11:00)이 지나 선착순 오픈 알림의 의미가 없어져 더 이상 알림을 발송하지 않는 상태 | PENDING, PROCESSING, RETRY 상태에서 11:00까지 FCM 발송 요청이 완료되지 않은 경우 | - | - | - |

**참고사항**

- **SENT의 의미:** 사용자가 실제로 알림을 확인 또는 클릭했다는 의미가 아님. 백엔드의 FCM 발송 요청이 성공적으로 처리되었다는 의미
- **발송 성공 기준:** FCM Web Push 발송 요청에 대해 대상별 성공 응답을 수신한 경우. 이때, SENT 처리하고 sent_at을 기록
- **재시도 기준:** 네트워크 오류, Timeout, FCM 일시 장애 등 일시적인 발송 오류가 발생한 경우, 재시도 처리. 최대 2회까지 재시도
- **만료 기준:** 11:00까지 FCM 발송 요청이 완료되지 않은 건을 만료 처리함. 이후에는 발송 또는 재시도 중단
- **무효 FCM 등록 정보:** FCM 발송 시, 등록 정보 형식이 잘못되었거나 만료·해제 등으로 더 이상 사용할 수 없는 것으로 확인되면 해당 FID 등록 정보를 삭제하고 추가 발송 및 재시도 중단
- **읽음 상태:** 읽음 상태는 알림 상태와 달리 DB에 별도 상태값으로 저장하지 않음. read_at 컬럼이 NULL이면 안읽음, 값이 존재하면 읽음으로 판단
